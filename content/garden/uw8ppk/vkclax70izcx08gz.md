# 了解Agent
:::color5
## 什么是 Agent?
+ **Workflow** 是 LLM 和工具被**预定义代码路径**编排的系统
+ **Agent** 是 LLM **动态指挥自己的过程和工具使用**、保持对”如何完成任务”的控制权的系统

:::

:::color1
## 何时(以及何时不)用 Agent
+ **Workflow** 给定义清楚的任务提供**可预测性和一致性**
+ **Agent** 是更好的选择 —— 当**灵活性和模型驱动的决策**在规模上需要时

**对许多应用来说,优化单次 LLM 调用 + retrieval + in-context examples 通常就够了**。

:::

## 智能体系统架构模式 简单->复杂
+ 增强型LLM（**基本积木**）
    - 信息检索、工具调用、记忆。模型主动运用能力
+ workflow 工作流
    - 提示词串联：将任务分解为一系列步骤，每次调用处理上一步的输出
        * 何时用：当任务能够被轻松且清晰地分解为固定的子任务时
    - 路由分配：对输入的内容分类，引导至对应的处理任务。能创建出更专业的处理指令，术业有专攻
        * 何时用：当面对那些具有明确分类、且这些分类更适合分开处理的复杂任务时
    - 并行化：**分解：**将大任务拆成独立的小任务，并行运行，汇总结果。**投票：**多次执行同一任务获得不同输出结果（可用于评估或者检查漏洞）
        * 何时用：当可以将拆分后的子任务并行处理以提高速度，或者需要从多个角度进行尝试才能获得更可靠的结果时
    - 编排器-工人：一个主LLM分解任务，交给子LLM，合成子LLM的结果。 
        * 何时用：任务较为复杂、且无法提前确定所需子任务的场景（编程中，需要修改的文件取决于具体任务）
    - 评估器-优化器：一个LLM生成响应，另一个在循环中负责评估并反馈
        * 何时用：有**明确的评估标准**，并且迭代优化能带来可观的改进效果
+ Agents：通常就是那些利用环境反馈机制进行循环处理的 LLMs 
    - LLMs 在关键能力上的成熟——理解复杂输入、进行推理和规划、可靠地使用工具以及从错误中恢复
    - 接受用户命令，与之进行交互式讨论**确定任务**，然后**独立规划和操作**，可能返回与用户交互获得更多信息或判断。执行中，会从环境中获取信息判断当前进度，可在检查点或遇到阻碍时暂停获取用户反馈。通常在完成任务时终止，或受停止条件控制
        * 何时用：在那些难以或无法预判所需处理步骤数量、且无法预先设定固定处理路径的开放式问题中

:::

# 从零开始设计Agent
## 设计
agent系统设计应该以简洁为主，从简单的方案开始

单次调用->单agent循环->agent工作流->多agent体系

减少agent与工具的交互次数，一次调用中提供最丰富和最直接可用的信息

极简版agent底层工具：读，写，编辑，命令行。拥有这些工具，基本能在本机完成大部分事情

上下文工程目前难关之一

### schema设计
Schema模糊程度 = 字段命名清晰度 + 字段类型约束 + 字段描述(description) + 取值范围(enum) + 必填/可选规则 + 字段之间关系

字段约束 > 类型约束 > 枚举约束 > 必填规则 > 字段名字

Schema不是只有字段名区别。 

**模糊Schema： **字段含义宽泛 + 约束少 → 灵活但不稳定 

**精确Schema：** 字段定义清晰 + 类型/格式/枚举约束 → 稳定可控

```json
{
  "location": "地点",
  "time": "时间"
}
```

```json
{
  "city": {
    "type": "string",
    "description": "查询天气的城市名称"
  },
  "date": {
    "type": "string",
    "description": "查询日期，格式 YYYY-MM-DD"
  },
  "unit": {
    "type": "string",
    "enum": ["celsius", "fahrenheit"]
  }
}
```

## 客户服务错位类型
+ **缺乏专注 - 跑题**

Agent的回答偏离主题，没有准确、清晰回答客户问题

```plain
客户："能帮我取消订阅吗？"

期望回答："好的，让我调出您的账户详情。能确认一下您的邮箱地址吗？"

错位Agent："很乐意帮您取消！您是要取消杂志订阅、流媒体服务，还是健身房会员？
我可以为这些提供通用建议..."

（实际上这是一个SaaS平台的客服Agent）
```

+ **范围不足 - 误解上下文**

Agent没有充分理解工作范围误解客户输入

```plain
客户："能帮我取消订阅吗？"

期望回答："好的，让我调出您的账户详情。能确认一下您的邮箱地址吗？"

错位Agent："很乐意帮您取消！您是要取消杂志订阅、流媒体服务，还是健身房会员？
我可以为这些提供通用建议..."

（实际上这是一个SaaS平台的客服Agent）
```

+ **幻觉 - 错误或虚构信息**

Agent生成错误或编造的答案	

```plain
客户："能帮我取消订阅吗？"

期望回答："好的，让我调出您的账户详情。能确认一下您的邮箱地址吗？"

错位Agent："很乐意帮您取消！您是要取消杂志订阅、流媒体服务，还是健身房会员？
我可以为这些提供通用建议..."

（实际上这是一个SaaS平台的客服Agent）
```

+ **不合规 - 违反业务规则**

Agent违反业务规则，造成财务、声誉或法律损害

```plain
客户："我对这次购买非常不满意。能给我全额退款并在下次订单中享受50%折扣吗？"

期望回答："我理解您的不满。关于退款，我可以在30天政策内处理退货。
至于额外补偿，我需要让您与主管联系，由他审核您的情况。您希望如何处理？"

错位Agent："当然可以！我理解您的不满。我已经处理了全额退款，
并在您的账户上应用了终身50%折扣。还有什么我可以做的吗？"

（实际上Agent没有权限提供此类补偿）
```

**影响**：这触及合规问题的核心。如果Agent越权，可能会给公司造成重大财务和声誉损失。

+ **不守规矩 - 忽略明确指令**

Agent忽略明确给出的指令

```plain
系统指令："在讨论账户详情之前，始终要求客户提供账号。"

客户："我的当前余额是多少？"

期望回答："让我帮您查询。出于安全考虑，请您提供账号好吗？"

错位Agent："您的当前余额是$2,847.32。还有什么我可以帮您的吗？"

（完全没有进行账户验证）
```

**影响**：不遵循业务指令会导致各种严重程度的问题，其中一些可能相当关键（如未经验证就讨论敏感信息）。

### agent loop
典型的工作流程如下：

```plain
初始上下文（系统提示词+用户请求）
    ↓
[agent loop开始]
    ↓
agent读取上下文 → 思考 → 决定行动
    ↓
执行工具/行动 → 获得结果
    ↓
结果追加到上下文
    ↓
[循环继续或结束]
```

细分到While循环到每一次迭代（Turn）可简单表示为：

```plain
初始化上下文（用户请求）
  ↓
┌─────────────────────────────────┐
│  Agent Loop                     │
│                                 │
│  ┌─────────────────────┐        │
│  │ Turn 1              │        │
│  │  LLM Call 推理 #1            │
│  │  → 解析LLM响应        │       │
│  │  → 执行工具1          │       │
│  │  → 返回结果，更新上下文 │       │
│  └─────────────────────┘        │
│           ↓                     │
│  ┌─────────────────────┐        │
│  │ Turn 2              │        │
│  │  LLM Call 推理 #2    │       │
│  │  → 执行工具2          │       │
│  │  → 返回结果，更新上下文 │       │
│  └─────────────────────┘        │
│           ....                  │
└─────────────────────────────────┘
  ↓
完成(当某一次Turn不再执行工具即表示完成，返回所有结果信息）
```

agent loop中包含以下几个相互关联的阶段：

1. **感知 (Perception)**：这是循环的起点。智能体通过其传感器（例如，API 的监听端口、用户输入接口）接收来自环境的输入信息。这些信息，即**观察 (Observation)**，既可以是用户的初始指令，也可以是上一步行动所导致的环境状态变化反馈。
2. **思考 (Thought)**：接收到观察信息后，智能体进入其核心决策阶段。对于 LLM 智能体而言，这通常是由大语言模型驱动的内部推理过程。如图所示，“思考”阶段可进一步细分为两个关键环节：
    - **规划 (Planning)**：智能体基于当前的观察和其内部记忆，更新对任务和环境的理解，并制定或调整一个行动计划。这可能涉及将复杂目标分解为一系列更具体的子任务。
    - **工具选择 (Tool Selection)**：根据当前计划，智能体从其可用的工具库中，选择最适合执行下一步骤的工具，并确定调用该工具所需的具体参数。
3. **行动 (Action)**：决策完成后，智能体通过其执行器（Actuators）执行具体的行动。这通常表现为调用一个选定的工具（如代码解释器、搜索引擎 API），从而对环境施加影响，意图改变环境的状态。

:::info

**turn：**以模型调用为界（模型调用中需要工具调用，工具调用和该模型调用属于一个turn

## 上下文工程
1. 截断工具的输出，完整信息保留在本地。提供给模型的信息：截断后的文本 + 本地的完整文件路径。 让模型自己评估是否读完整的
2. 上下文压缩（超过模型上下文（会报错），上下文太长会变笨）
    1. 什么时候压？
        1. 设置token阈值，token可用量低于阈值，压缩
        2. 在上一轮问题结束后主动压缩
    2. 怎么压？
        1. 按具体的场景设计固定模板
    3. 替换旧消息
        1. 下一次对话时，用压缩后的结果替代被压缩的上下文

要通过合理的编排，提高缓存命中率

## 维护工具调用
1. 定义工具schema
    - name 工具名
    - description 用途
    - 参数 + 类型
    - 何时使用
2. schema塞进提示词，调用工具
    - schema 拼进 system
    - 连同历史发给模型
    - 模型返回 toolcall
3. 程序解析执行
    - 取 tool name
    - 取 arguments
    - 本地执行工具

**保障工具调用的准确性**

1. 参数验证
    1. 模型返回JSON调用指令时，会序列化字符串，检测到后转化为json
    2. schema类型转换。参数要求数值型，结果返回了文本型，piagent自动转化
2. 调用前安全检查
    1. 是否有危险指令
    2. 校验返回的结果是否需要脱敏
3. 调用时错误处理
    1. 把工具的错误信息返回给模型，agent循环不会中断，且可能重新生成正确的调用
    2. 根据不同工具，尽可能设置预定好的错误信息，没有也要设置通用的错误信息
4. 调用后结果处理

## MCP（Model Context Protocol）
**MCP（模型上下文协议）是一种开源标准，用于将人工智能应用与外部系统连接起来。**

实现方式：stdio 和 Streamable HTTP

+ stdio，宿主程序直接拉起本地子进程，走标准输入输出，本地开发和桌面 Agent 的标准姿势，代价是单机单客户端，信任关系只在进程级。
+ Streamable HTTP，单个 HTTP 端点，POST 发请求，GET 建流收推送，支持会话保持和断线恢复，配 OAuth 2.0，企业内集中部署、多团队共享，官方推荐的远程方式只有它。

## 所有工作流的通用核心原则
1. **按需增加复杂度**：仅当简单方案无法满足需求时，才使用多步骤工作流，避免无意义的复杂设计；
2. **可组合定制**：各工作流并非硬性规范，可根据实际场景灵活组合、调整；
3. **性能量化**：以实际性能指标为依据，持续迭代优化工作流实现方案。

#### RRF算法
RRF 是一种简单但非常有效的排序融合算法。它的核心思想是：**我们不关心原始分数是多少，只关心一个文档在各个列表中的“排名位置”**。

排名越靠前，说明该方法认为这个文档越重要。

由于向量检索（-1～1）和关键词检索（0～100）之间的评分差距很大，不能直接通过综合二者的评分去获得一个更好的排序。

所以我们有了RRF算法

**RRF 的工作原理：**

1. 对于每一个搜索引擎或检索方法返回的结果排序。
2. 查看某个特定文档在每个列表中的排名 (rank)。
3. RRF 会给每个文档一个基于其排名的“融合分数”。这个分数是这样计算的：  
取排名的倒数 (reciprocal of the rank)。例如，排名第 1 就是 1/1，排名第 2 就是 1/2，在第 10 名就是 1/10。
4. 为了避免排名很靠后 (比如第1000名) 的文档因为分母过大导致其影响力过小，同时给予所有参与排名的文档一个基础权重，RRF 在分母上加了一个常数 `k`。
5. 将一个文档在所有不同列表中的“倒数排名分数”加起来，得到这个文档最终的 RRF 分数。
6. 最后，根据所有文档的 RRF 总分重新排序，得到最终的混合检索结果。

**RRF 公式**

![](/images/yuque/8dda0d023e3513ea.png)

![](/images/yuque/7df4c58db02536c3.png)

在多查询 Hybrid Retrieval 场景下，每个“子查询 × 检索方式”都会产生一条独立的有序结果列表。

例如 3 个子查询结合 Dense Retrieval 与 Sparse Retrieval，会得到 6 条 ranked lists。

RRF 会将这 6 条列表视为 6 个独立投票源，对同一文档在不同列表中的排名贡献进行累计：

Score(d) = Σ 1 / (k + rank_i(d))

最终根据累计得分进行全局排序，并截取 Top-K 结果。

**Auto Memory 结构**

存放在`~/.claude/projects/<项目路径转 slug>/memory/`  
~/.claude/projects/-Users-yllmis-go-projects-code-agent/memory/  
├── MEMORY.md                  # 索引，常驻上下文  
└── 文件.md     # 具体记忆，按需加载  
四种记忆类型

+ MEMORY.md 只有一行一条的索引：- 标题[文件.md] — 一句话描述，靠描述决定何时点开
+ 记忆文件 用 frontmatter 标 type，正文末尾写 Why（为何记）和 How to apply（何时用）

**四种类型**

| type | 存什么 |
| --- | --- |
| user | 你是谁：角色、专长、偏好 |
| feedback | 你对我工作方式的纠正/要求 |
| project | 项目目标、决策、阶段 |
| reference | 外部资源指针（URL、看板等） |

**该存 / 不该存**

该存：跨会话仍有用、且不在代码里的偏好、约定、状态、指针  
不该存：代码里已有的结构/逻辑、密钥隐私、会话临时状态、重复 CLAUDE.md 的内容、未验证的猜测

判断标准：一年后还有用、且读代码/仓库拿不到，才进 auto memory。

**加载方式**

会话启动  
  ├─ CLAUDE.md     → 全文注入  
  ├─ MEMORY.md     → 索引常驻  
  └─ 记忆正文       → 相关时才 Read

这样记忆可以很多，常驻成本只有索引行。

与 CLAUDE.md 的分工

+ CLAUDE.md：团队共享、稳定规范（进 git）
+ Auto memory：个人化、来自对话观察（不进 git，按项目隔离）
+ Plan/Tasks：只管"这次怎么干"，不是长期记忆

怎么主动用

+ 记住："记住：以后 Go 外部调用一律包 context.WithTimeout"
+ 忘掉："忘掉 X" / 指定删 feedback_bagu_rules.md 里某条
+ 直接编辑：/memory 命令，或手动改 MEMORY.md 和记忆文件
