## 并发
### sync.WaitGroup包
> 每个协程开始前要调用`Add(1)`方法
>
> 每个协程结束时要调用`Done()`方法，表示任务已经执行完成
>
> 主协程中要调用`Wait()`方法，等待所有协程结束
>

```go
// 并发模式 第二种 使用sync.WaitGroup
func GetVoteV5(id int64) (*VoteWithOpt, error) {
	var ret Vote

	wg := sync.WaitGroup{}

	wg.Add(1)
	go func() {
		defer wg.Done()

		if err := Conn.Raw("select * from vote where id = ?", id).Scan(&ret).Error; err != nil {
			fmt.Printf("查询失败, err:%s\n", err.Error())
		}

	}()

	opt := make([]VoteOpt, 0)
	wg.Add(1)
	go func() {
		defer wg.Done()

		if err1 := Conn.Raw("select * from vote_opt where vote_id = ?", id).Scan(&opt).Error; err1 != nil {
			fmt.Printf("查询选项失败, err:%s\n", err1.Error())
		}

	}()

	wg.Wait()

	return &VoteWithOpt{
		Vote: ret,
		Opt:  opt,
	}, nil
}
```

### 并发模型
> Go语言的高并发能力源于其轻量级协程（goroutine）和高效的GPM调度模型。GPM分别代表Goroutine、Processor和Machine，是Go运行时实现并发调度的核心。
>

#### 核心原理和GPM解析
##### GMP模型结构
+ **G**：代表一个协程，包含执行栈和状态信息；
+ **P**：逻辑处理器，持有可运行G的本地队列；
+ **M**：操作系统线程，负责执行G代码。

##### 调度机制特点
+ **工作窃取**：空闲P会从其他P队列尾部“窃取”G，提升负载均衡；
+ **系统调用阻塞处理**：M在系统调用时释放P，允许其他M接管P继续调度；
+ **抢占式调度**：基于时间片和函数调用协作点实现G的主动切换。

| 组件 | 作用 | 数量限制 |
| --- | --- | --- |
| G | 并发任务单元 | 无上限（内存决定） |
| P | 调度上下文 | GOMAXPROCS（默认CPU核数） |
| M | 执行实体 | 动态增减，匹配P |

#### 使用goroutine池控制并发数量并避免资源浪费
##### 并发控制的核心思想
使用预启动的worker池接收任务，避免频繁创建销毁goroutine。任务通过channel分发，实现生产者-消费者模型。

```go
type Pool struct {
    tasks chan func()
    done  chan struct{}
}

func NewPool(workerNum int) *Pool {
    p := &Pool{
        tasks: make(chan func(), 100),
        done:  make(chan struct{}),
    }
    for i := 0; i < workerNum; i++ {
        go func() {
            for task := range p.tasks {
                task()
            }
        }()
    }
    return p
}
```

`tasks`通道缓存待执行函数，`workerNum`决定最大并发数。每个worker从channel读取任务并执行，实现协程复用。

#### 限流算法在100路并发场景下的选型与实现
在高并发系统中，面对100路并发请求的瞬时冲击，合理选择限流算法是保障服务稳定性的关键。常见的限流策略包括计数器、滑动窗口、漏桶和令牌桶算法。

##### 算法对比与选型考量
| 算法 | 平滑性 | 实现复杂度 | 适用场景 |
| --- | --- | --- | --- |
| 固定窗口计数 | 低 | 简单 | 请求波动小的场景 |
| 滑动窗口 | 中 | 中等 | 需精确控制的突发流量 |
| 漏桶 | 高 | 较高 | 强制匀速处理 |
| 令牌桶 | 高 | 高 | 允许短时突发 |

对于100路并发，推荐使用[**令牌桶算法**](https://www.yuque.com/yllmis/uw8ppk/xdrapqseh2ehgwv9)，因其既能控制平均速率，又允许一定程度的突发流量。

##### 核心实现代码（Go语言）
```go
type TokenBucket struct {
    capacity  int64 // 桶容量
    tokens    int64 // 当前令牌数
    rate      int64 // 每秒生成令牌数
    lastTime  time.Time
}

func (tb *TokenBucket) Allow() bool {
    now := time.Now()
    delta := (now.Sub(tb.lastTime).Seconds()) * float64(tb.rate)
    tb.tokens = min(tb.capacity, tb.tokens+int64(delta)) // 补充令牌
    tb.lastTime = now
    if tb.tokens >= 1 {
        tb.tokens--
        return true
    }
    return false
}
```

上述实现通过时间差动态补充令牌，`rate`决定系统吞吐上限，`capacity`控制突发容量。在100并发场景下，设置`rate=80`、`capacity=100`可有效削峰填谷，避免资源过载。

## 内存逃逸
在Go语言中，内存分配有两种方式：栈分配和堆分配。栈分配是在函数调用时为局部变量分配内存，当函数返回时，这些内存会自动释放。而堆分配则是通过 new 或者 make 函数动态分配内存，需要手动进行释放。

内存逃逸是指原本应该在栈上分配的内存被分配到了堆上。这意味着即使函数返回后，这部分内存也不会被自动释放，需要等待垃圾回收器（gc）来回收。

**原因**

### 内存逃逸的原因
内存逃逸的主要原因是在函数返回后，局部变量仍然被外部引用。以下是一些可能导致内存逃逸的情况：

+ 变量的生命周期超出了其作用域，当一个变量在函数外部被引用，比如被赋值给一个包级别的变量或者作为返回值，这个变量就会发生逃逸。
+ 大对象的分配，对于大型的数据结构，Go 有时会选择在堆上分配内存，即使它们没有在函数外部被引用。
+ 闭包引用，如果一个函数返回一个闭包，并且该闭包引用了函数的局部变量，那么这些变量也会逃逸到堆上。
+ 接口动态分配，当一个具体类型的变量被赋值给接口类型时，由于接口的动态特性，具体的值可能会发生逃逸。
+ 切片和 map 操作，如果对切片进行操作可能导致其重新分配内存，或者向 map 中插入数据，这些操作可能导致逃逸。

**检测**

`go build -gcflags="-m"` 查看逃逸分析结果。

```go
package main

import "fmt"

type User struct {
	Name string
}

func main() {
	var user *User
	user = getUser()
	fmt.Println(user.Name)
}

func getUser() *User {
	u := User{Name: "Alice"}
	return &u
}
```

**如何避免**

+ 严格限制变量的作用域。如果一个变量只在函数内部使用，就不要将其返回或赋值给外部变量。
+ 使用值而不是指针，当不必要的时候，尽量使用值传递而不是指针传递。
+ 池化对象，对于频繁创建和销毁的对象，考虑使用对象池技术进行复用，减少在堆上分配和回收对象的次数。
+ 尽量避免在循环或频繁调用的函数中创建闭包，以减少外部变量的引用和堆分配，避免使用不必要的闭包，闭包可能会导致内存逃逸。
+ 优化数据结构，使用固定大小的数据结构，避免使用动态大小的切片和 map。比如使用数组而不是切片，因为数组的大小在编译时就已确定。
+ 预分配切片和 map 的容量，如果知道切片或 map 的大小，预先分配足够的容量可以避免在运行时重新分配内存。

### 三色标记
![](/images/yuque/ab9562eaa24b81c1.svg)

#### 标记过程
1. **初始化**：所有对象为白色，根对象标记为灰色
2. **标记循环**：
    - 从灰色对象集合中取出一个对象
    - 将其标记为黑色
    - 将其直接引用的白色对象标记为灰色
    1. **并发标记**：GC 从队列中取出灰色对象，将其引用的子对象标记为灰色（若子对象为白色），然后将当前灰色对象标记为黑色。
3. **结束条件**：灰色对象集合为空
4. **清除**：回收所有白色对象

#### 三色不变性
为了保证并发标记的正确性，必须维护**三色不变性**：

+ **强三色不变性**：黑色对象不能直接指向白色对象
+ **弱三色不变性**：黑色对象可以指向白色对象，但必须存在从灰色对象到该白色对象的路径

  
GC 触发条件：

+ 堆内存增长达到 GOGC 设定的阈值（默认 100%，即堆翻倍时触发）
+ 超过 2 分钟未触发强制 GC（runtime.GC()）
+ 手动调用 runtime.GC()

三色标记法：

+ 白色：未被扫描，标记结束后是垃圾
+ 灰色：已扫描但其引用对象未全部扫描
+ 黑色：已扫描且引用对象全部扫描完
+ 流程：所有根对象（栈、全局变量）标灰 → 从灰色集合取出变黑色，其引用的白色变灰色 → 灰色为空时结束 → 清除所有白色对象

写屏障（Write Barrier）：

+ 三色标记和用户代码是并发执行的，可能出现漏标（用户代码在标记过程中修改了引用关系）
+ 写屏障在指针赋值时拦截，保证"不会把存活对象误标为白色"
+ Go 1.8+ 使用混合写屏障：结合 Dijkstra 插入屏障 + Yuasa 删除屏障，避免栈重扫描，STW 时间降到亚毫秒级

分代假设：Go 没有真正的分代 GC，但把对象按大小分为微对象（<16B，走 mcache 的 tiny allocator）、小对象（16B~32KB，走mcache）、大对象（>32KB，直接走 mheap）。

记忆：三色标记灰到黑，写屏障防漏标；混合写屏障 1.8+，STW 亚毫秒；微小大三档分配。

## Struct字节对齐
#### 规则一：数据自身对齐（Data Member Alignment）
每种基本数据类型都有自己的“对齐模数”（通常等于它的占用字节数 `sizeof(type)`）。

+ `char`（1 字节）：对齐模数为 1，可以放在任意地址。
+ `short`（2 字节）：对齐模数为 2，其起始地址必须是 2 的倍数（即末位必须为偶数）。
+ `int`（4 字节）：对齐模数为 4，其起始地址必须是 4 的倍数（0, 4, 8, 12...）。

#### 规则二：结构体成员偏移对齐（Struct Member Offset Alignment）
结构体内的成员按定义顺序先后放置，但编译器会在各个成员之间插入“填充字节（Padding）”。填充的唯一目的是**保证每个成员距离结构体起始位置的“偏移量（Offset）”是它自身对齐模数的整数倍**。

#### 规则三：结构体整体大小对齐（Structure Overall Alignment）
结构体的最终**总大小（Total Size）必须是其内部所有成员中“最大对齐模数”的整数倍**。如果算完最后一个成员后，总大小不满足这一条件，编译器会在结构体的末尾继续追加填充字节。这是为了确保当我们创建一个包含该结构体的数组时，数组中的每一个元素都能满足对齐条件。
